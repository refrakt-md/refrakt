# v0.46.0 · The theme contract

[All releases](/releases)

A theme renders a vocabulary and configures no rune ({% ref "ADR-043" preview="drawer" /%}); a plugin rune speaks
the same vocabulary, and only its novel parts bring their own structure, in tokens
({% ref "ADR-044" preview="drawer" /%}). Both decisions were accepted on 2026-10-28. This milestone builds what
makes them checkable.

## Changes

- A composition's narrative field is checked when its definition loads (ADR-047). A content-model field whose `match` names only the editorial runes (`tag:textblock`, `tag:mediatext`) is the rune's narrative field: the story a template can place between the rune's own parts. Two rules are now enforced:
  - **One per rune.** A definition with two narrative fields is rejected (`narrative-field-twice`).
  - **Never structured data.** A schema table that maps the narrative field is rejected (`narrative-field-mapped`).
- A field that mixes editorial runes with other matches is not a narrative field. `refrakt inspect` and `refrakt reference` name the narrative field. The rune-authoring patterns guide and the composed-runes guide document it.
- Two checks make ADR-043's and ADR-044's contracts checkable. Both are reports, not gates.
  - **`refrakt theme coverage`** reports, for every value of the theme vocabulary, whether a theme's CSS styles it, leaves it to the base stylesheet (`@refrakt-md/skeleton`), or nothing does. The vocabulary is each meta type, sentiment, zone layout, sequence, section role, media kind and universal-axis value. It is read from the registries that define it (`themeVocabulary()` in `@refrakt-md/runes`; `META_TYPES`, `SENTIMENTS`, `LAYOUT_PRIMITIVES` and `vocabularyCoverage()` in `@refrakt-md/transform`), so a new value appears without updating anything. Lumina runs it as a test, with its unstyled values recorded as a set that may only shrink.
  - **`refrakt plugins validate`** now reports, for a plugin's themed runes, the elements that carry no vocabulary role (ADR-044's tier 3), and the literal colours, sizes and font stacks in its `styles/` stylesheets (`novelElements()`, `lintTokenOnly()`). A plugin whose stylesheets have none is theme-portable.
  - **Baseline:** `npm run plugins:vocabulary` records both for the nine first-party plugins in `contracts/plugin-vocabulary.json`. This is the baseline Lumina's per-rune CSS drains from.
- The engine no longer adds `rf-badge` to field values (ADR-043 decision 3). A value states what it is (`data-meta-type`, and `data-meta-sentiment` when its field maps one), and the base stylesheet draws `status`, `category` and `tag` values as pills by that attribute. Every value is now one element: a definition-list `<dd>` holds a `<span data-meta-type>` for every kind, where a bare value used to put the type on the `<dd>` itself. `{% badge %}` keeps its `rf-badge` class, and the pill rule covers it. Lumina renders every page unchanged.
- **For theme authors:** a rule on `.rf-badge` now reaches only `{% badge %}`. Style field pills with `[data-meta-type="status" | "category" | "tag"]`, and a definition-list value with `dd > [data-meta-type]` rather than `dd[data-meta-type]`.
- All of `metaFields` is identity (ADR-043 decision 2). A theme that overrides any part of a rune's meta fields (`metaType`, `label`, `sentimentMap` or `transform`) has the override reported and dropped, as it already was for `metaType` alone. A label is copy, a sentiment map says what a value means, and a transform says how it is formatted: all are claims about the content, not its look. No first-party theme overrides them.
- **For third-party themes:** move a label, sentiment or format change into the rune's definition (or the plugin), or style the field through `[data-field="…"]`, `[data-meta-type="…"]` and `[data-meta-sentiment="…"]`. `blocks`, which fields are grouped and how they are arranged, stays the theme's.
