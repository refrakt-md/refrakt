## 1. Summary: the five most important things

1. **The docs never say what 1.0 is, and what they describe is not "small" or "built".** `M:docs/concepts/principles.md:10-13` says 1.0 ships "from what is built and settled, not from what is planned" and that features graduate only after use in refrakt. But `content-models.md:7-9` is a "leaning revision ... made with fresh eyes", and the write path, addresses, value types, explicit slots, compact forms, write templates, Standard Schema, kits, dimensions, document shapes, middleware and a second syntax are all new design. `R:docs/concepts/use-cases.md:61` confirms refrakt today "edits files with regular expressions". SPEC-199 has a concrete, small "What 1.0 contains" table (SPEC:111-127) that the docs dropped. Either restore that table in the docs, or admit the graduation rule starts after 1.0. As written, a reader cannot tell which of 14 pages they could build against.

2. **The write path rests on two unproven foundations: positions and unambiguous inference.** "Every byte outside them stays as it was" (`M:writing.md:4-5`) needs byte ranges for every node, including inline ones. `M:syntax.md:16` claims Markdoc has positions on "every node"; the notes say "line ranges on nodes" and list checking it as a to-do (NOTES:1692, 1717). Comark has component lines only. Separately, the matching rule ("binds each to the first field that accepts it", `M:content-models.md:22`) is not specified well enough to predict or to invert, and the round-trip rule exists because inference is ambiguous. I would (a) require content models to be deterministic in the XML-schema sense and report violations when a shape loads, and (b) decide the parser question by the position requirement before anything else.

3. **Rivière depends on Marquise features that Marquise's docs do not define, and the two repositories disagree on rules.** `ref` and identity types, deferred shapes, dependency tracking and the `summary` projection are attributed to Marquise by Rivière (`R:overview.md:26-36`) but `ref`, identity and deferred shapes have no definition in Marquise's pages. Rivière's shape examples break Marquise's Decided naming rule (`blockedBy`, `R:references.md:10`), use bare-id addresses Marquise's grammar cannot parse (`WORK-123.criteria`, `R:context-bundles.md:17`), and put an undeclared core key on an attribute (`acyclic`, `R:references.md:18`). "After Marquise 1.0, public API only" (`R:overview.md:12-14`) therefore freezes seams before their only second client exists. Prototype the plan rebuild before the freeze.

4. **Records are neither complete nor syntax-neutral.** A block field is "its Markdown source" (`M:records.md:35`), so a nested `{% callout %}` inside `section.body` appears in the record only as Markdoc (or Comark) text inside a string. A search index, a database sync or an API consumer then needs a Marquise parser for the right syntax. This also breaks "findings, extracted fields and edit targets share one address" (`M:writing.md:9`): `section.body.callout.title` addresses into a string. Value types have the same problem in small: `"$29"` becoming `{amount: 29, currency: "USD"}` guesses the currency and stores money as a float.

5. **Several safety and coordination claims are stronger than the mechanism.** "Two agents cannot claim the same item" (`R:README.md:72-73`) holds only inside one working tree: two clones that both set `status: in-progress` produce identical edits, which git merges without conflict. Multi-file applies are not atomic and nothing says what state a failure leaves. Untrusted content can query any collection through `{% collection %}` or `{% expand %}`. A document can choose its own shape over the host's ("frontmatter winning", `M:shapes.md:84`). Context-bundle delimiters are plain Markdown headings that content can forge. And the trust boundary is marked Leaning (`M:trust.md:9`) while it is the README's headline promise and a listed public contract (`M:principles.md:59`).

## 3. Fresh perspectives

Confidence: high / medium / low is my confidence that the change is worth making.

**1. Treat the content model as a grammar and require it to be deterministic. (high)**
A content model is a regular expression over block-node types, which is what DTD, XML Schema and RELAX NG content models are, and what ProseMirror's content expressions are (recalled). XML Schema's "Unique Particle Attribution" rule requires that each node can be assigned to one particle with one node of lookahead. Adopting it means: a shape whose model is ambiguous (two adjacent optional paragraph fields) fails at load with a finding naming the pair. That turns the round-trip fallback from a routine event into a rare one, makes writes predictable, and gives "what is allowed next" for completions for free. RELAX NG's derivative method also answers the Open question at `M:validation.md:60-63`: partial input is valid if some completion exists, so "missing" is reported only when the tag closes. It would change `content-models.md` (a normative algorithm), `writing.md` (fewer fallbacks), and remove most of the need for "refused with a finding".

**2. State the write path as lens laws, and add the missing one. (high)**
The round-trip rule (`M:writing.md:56-57`) is the "PutGet" law plus a frame condition. The other half, "GetPut", is missing: writing back the value just read produces zero edits. Without it, a sync from a store rewrites every file it touches. Prior art: bidirectional lenses (Boomerang), `recast` for JavaScript, `jsonc-parser`'s `modify` returning text edits, `toml_edit`, `ruamel.yaml` (all recalled). Each needed a lossless syntax tree with exact ranges, which leads to idea 3.

**3. Choose the parser by the position requirement. Consider micromark/mdast as a third candidate. (medium)**
Recalled: markdown-it gives line maps on block tokens and nothing on inline tokens, and Markdoc is built on it, so "set this link's href in a list item" needs ranges Markdoc does not supply. Comark is weaker still. micromark and mdast give full start and end offsets on every node, and `remark-directive` implements the generic-directive syntax (`::name{attrs}`) that Comark and MDC descend from. If the write path is a pillar, I would run one spike that changes one inline value in each of the three and compare the edits, then decide. I would also drop the second syntax from 1.0 entirely: the runtime is cheap, but every example, the language server and the formatter double.

**4. Cut 1.0 to the read path. (high)**
Proposed 1.0: shape files (attributes, content model, `as`), validation with findings, typed props, records as JSON plus JSON Schema, the plain presentation, one renderer contract, one syntax, `validate` and `types`. Everything else has its own unsettled design and its own contract surface: the write path, addresses for writing, compact forms and write templates, kits, dimensions, presets, bindings, hydration vocabulary (`M:rendering.md:95`, which takes over something every host already does and so fails the docs' own test at `principles.md:26-27`), middleware, document shapes, migrations, `computes`, MCP, the Comark front end. "No experimental flags" plus "semver from 1.0" plus the contract table at `principles.md:52-59` means each of these is frozen the day it ships. If the write path must be in 1.0, ship set and unset of attributes and of explicit-slot fields only, where the inverse is trivial.

**5. Reverse the order: build the plan rebuild on a pre-1.0 Marquise. (high)**
The acceptance test for Rivière (`R:overview.md:56-61`) is also the best test of Marquise's seams, and it needs things Marquise's docs lack: `ref`, identity, deferred shapes, task-list items with a `done` value, sections bound by heading text with aliases ("Blocked by", "Depends on"), and list-valued references in content. Finding these after 1.0 means majors. A throwaway Rivière prototype on Marquise 0.x costs little and tells you which seams are wrong.

**6. Make a block field a structured value, not a string. (medium)**
Minimum: `{ markdown, text, shapes: [...] }`, where `shapes` lists the nested records with their addresses. That keeps the lossless source, gives search a plain-text form, and makes records independent of the syntax. Sanity's Portable Text is the precedent for custom blocks inside rich text. In untrusted mode the `markdown` value must be the sanitised form, or consumers that render it inherit raw HTML that Marquise's renderers would have refused.

**7. Value types should keep the author's text. (medium)**
`3:45` versus `3 min 45 s`, `$29` versus `29 USD` versus `29,00 €`, `11/12/2026`. A formatter cannot recover the author's style from `PT3M45S` (`M:records.md:37-39`). Store `{ value, source }` or re-detect the style from the existing text when writing. Represent money as a decimal string or minor units, not a JSON number. Require an explicit currency or a document locale; never infer `USD` from `$`. I would keep only `number`, `date`, `url` and `boolean` in core.

**8. Findings should carry machine-applicable fixes, and be exportable as SARIF. (high)**
"Read a finding, edit at its address" (`M:validation.md:19-20`) still leaves the agent to invent the edit. ESLint, rustc and the language server protocol attach suggested edits with an applicability level. Add `fixes: Operation[]` to a finding where one is known (`attribute-type-invalid` with one close match, `slot-unknown` with an edit distance of one). SARIF output gives GitHub code scanning for free.

**9. Use the language server protocol's `WorkspaceEdit` as the changeset format. (medium)**
It already has versioned per-document text edits, create, rename and delete file operations, and change annotations with "needs confirmation". That fills the gap in I16, and the language server and editors can apply a Rivière changeset with no adapter.

**10. Concurrency: be honest about scope, and make multi-file applies recoverable. (high)**
(a) The hash check is a check-then-write inside one process; two processes on one tree can still race, and two clones cannot see each other at all. Say "within one working tree". For real claims across clones, either write the claimant's identity (`assignee: agent-7`) so that two claims conflict in git, or claim by pushing a ref and letting the remote reject the second. (b) `rv.apply` should verify every hash first, write to temporary files, then rename, and roll back on failure. "Git covers that" is only true on a clean tree. (c) Whole-file hashes refuse an edit when a person fixed a typo elsewhere in the file. Because operations are addressed, an optional rebase is cheap: if each target resolves to identical content in the new version, re-resolve and apply.

**11. Rivière's query shapes are a data-exposure channel in untrusted content. (high)**
`R:shapes.md:50-51` limits engines and `limit`. It does not limit which collections an untrusted author may read. On a site with a public and an internal collection in one corpus, `{% collection "internal" %}` or `{% expand "HR-12" /%}` in a public page publishes internal content. Add a per-collection flag for "readable from untrusted content", default off.

**12. Context bundles need delimiters that content cannot forge. (medium)**
The format at `R:context-bundles.md:63-78` separates entities with `## ID · shape · via · level` headings. An entity's own Markdown can contain the same heading, an "Omitted" section, or the opening comment. Use a per-bundle random token in the delimiters, or return entities as JSON strings and let the Markdown view be derived. Also: "characters divided by four" (`:54`) undercounts badly for Chinese, Japanese and Korean text; and "depth 1 is `full` where declared" makes the default bundle large for hub entities.

**13. Do not invent an expression language or a query engine seam. (medium)**
For `computes`, adopt CEL, JSONata or JMESPath rather than "Marquise's own expression vocabulary". For queries, replace the engine seam (`R:queries.md:49-57`) with an export: `riviere export --jsonl` or `--sqlite`, and let people use DuckDB or SQLite. That removes a contract, removes the determinism rules for third-party operators, and serves the "I want more vocabulary" user better. People will ask for OR across fields in the first month (GitHub's issue search added it, recalled); plan the parser now.

**14. Declaration merging makes the type registry global. (low to medium)**
`declare module 'marquise' { interface ShapeRegistry ... }` (`M:records.md:83-87`) is one registry per TypeScript program. Two shape sets in one program (a monorepo with two sites, a test that loads a fixture set) cannot both be typed. TanStack Router has the same limit. Offer `createMarquise<Shapes>()` as the alternative from the start. Also consider a TypeScript builder that produces the serialisable shape form, for teams that prefer inference to a generation step.

**15. Internationalisation and accessibility gaps. (medium)**
- The plain presentation renders an `as: inline` heading as `<div data-slot="headline">` (`M:rendering.md:44`), so a page of unbound shapes has no headings for assistive technology. Render heading-matched fields as headings at a level derived from nesting.
- Sections bound by heading text ("Blocked by") and key-based addresses (`ingredients["Salt"]`) are language-bound. A translated document has different addresses.
- The same entity in two locales is a duplicate id in one collection. Identity needs a locale part, as Astro's and Nuxt's i18n have.
- "Exact" selector matching needs a stated Unicode normalisation and case rule; ids on case-insensitive file systems need one too.
- `git` line-ending conversion changes bytes and hashes between machines; say what the content hash is taken over.

**16. Prior art worth reading before building. (medium)**
- Keystatic (git-based, Markdoc content components with schemas) and TinaCMS (git-backed, typed rich-text templates, a query layer over files): closest to Marquise plus Rivière (recalled).
- Sphinx-Needs and Doorstop: requirements as typed objects in docs with typed links, filters and traceability checks; this is Rivière's "regulated industries" row, already built, with lessons on link types and id schemes (recalled).
- Obsidian Dataview and Bases: the demand for queries in content, and what authors expect the syntax to look like; also `[[wikilinks]]` as the mention syntax people already type.
- SHACL and ShEx call their graph schemas "shapes". Readers from that world will assume a relation. An export of shapes to JSON-LD contexts, with addresses as `@id`, would make the name an asset.
- DITA and DocBook: typed document bodies have existed for decades, so "nothing else types the body this way" (`M:overview.md:22`) should be narrowed to "for Markdown".
- Model APIs' strict structured output accepts only a subset of JSON Schema (recalled). "Which model APIs accept" (`R:use-cases.md:19-20`) needs a strict-profile emitter.
- One MCP tool set per collection: clients degrade as tool counts grow. Default to generic tools with the schema as a resource.

**17. Opportunities.**
- A git merge driver that merges two versions of a document by address rather than by line. It suits the agent use case better than refusal.
- `marquise diff a b` producing a record-level diff ("status: ready to done") for pull-request review and changelogs.
- Shape inference: propose a shape from a folder of existing Markdown. This is the fastest onboarding for a team with content and no schema.
- Publish each shape as a grammar for constrained decoding (the docs say "the AI grammar" at `M:shapes.md:29` and never define it).

**What users will expect on day one and will not find:** a playground; a Marquise-only Astro or Next recipe; a way to adopt one tag at a time in an existing Markdoc project; error display in the dev server; test helpers; a JSON Schema for shape files so YAML editors complete them; an answer for code blocks, tables and task lists.

## 4. Questions to answer before building

1. What exactly is in Marquise 1.0? Is the write path in it? Are records?
2. Does any candidate parser give byte ranges for inline nodes? If not, who builds the position layer, and is it a contract?
3. What is the normative matching algorithm, and are ambiguous content models rejected or tolerated?
4. Where is an id declared, what characters may it contain, and where is it unique (document, collection, shape, locale)?
5. Is a record a tree or a flat list? Where do nested shapes inside a block field appear?
6. Is `doc.tree` (and therefore every record and the Rivière snapshot) a function of host values such as `$locale`? If so, what is the snapshot's key?
7. Which callbacks may be async (`resolveAsset` usually is), given "load is the only async step"?
8. What does `rv.apply` leave behind when the fourth of seven files fails?
9. How does a second changeset built from the same snapshot apply after the first?
10. Which process holds the corpus for a one-shot CLI call, and what is the cold-start cost at 10,000 documents?
11. What may untrusted content read through `collection`, `ref` and `expand`?
12. How are acceptance criteria (task-list items), heading-named sections with aliases, and list-valued references expressed in a content model? The acceptance test needs all three.
13. Does refrakt adopt the new shape format and addresses before Marquise 1.0, or does "the same shapes and content work in both" (`M:principles.md:16`) wait?
14. Who maintains two front ends, five renderers, a language server, a Vite base, two satellites in separate repositories, and then Rivière? Is that one person?
15. What is the migration story when a shape changes meaning but old and new content both validate, given "content carries no version stamps" (`M:extending.md:111`)?

### Where I still disagree with a recorded decision

- **Identity is the address** (NOTES:112-115, A1). The reason given is that refrakt keyed entities by URL. That argues against URLs, not for file paths. `(collection, id)` is what `c.get`, the Astro mapping and V5 already use; a move should not change identity.
- **Rivière after Marquise 1.0, public API only** (M7). NOTES:159-161 is itself a list of what Rivière needs from Marquise before 1.0, which shows the dependency runs the other way in time. Build the prototype first.
- **No atomicity across documents** (NOTES:2594-2595). Fine as a guarantee to disclaim; wrong as a reason not to make `apply` verify-then-write with rollback.
- **Optimistic concurrency as the coordination mechanism** (NOTES:515-516). It is local to one tree. The task-queue use case needs more, or a narrower claim.
- **Dots over JSON Pointer** (A1). I accept the choice; the grammar gaps (bare-id roots, id characters, escaping) remain.
- **The grammar decided before the catalogue** (V6 with V8). The record has the same tension as the docs.
- **SPEC-199's 1.0 table** is the right size, and I prefer it to the docs' implied scope. But it contains no records, no write path and no value types, so the tagline "Markdown in, typed data out" would describe a release that outputs props only. Either add extraction (small, as M2 argues) or keep "typed props out" for 1.0.
